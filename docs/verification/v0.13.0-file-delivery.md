# opv v0.13.0: live checks for #136 (A4, A5), runbook

This is the runbook for the last live checks of #136. The owner runs it top to bottom in one session. **Status: kit only, not run yet.** Nothing in this file or its directory has touched Fly, 1Password or a cluster. The `live-record` lane fills the results tables (§8) from the session's evidence.

- **A4** is the tagged-release verification. It runs `docs/design/delivery-transports.md` §12.1 V1–V17 against the published **v0.13.0** release (tag `v0.13.0` = `ff81d31c141389dc99620f21de54fa2cc1534993`), using canary values only.
- **A5** is the Fly live check. It answers F1–F4 of §7.3 (`journeeze-saas#274` §1). A one-off `fly machine run … --file-secret` machine runs inside the staging fleet app with a canary file secret, and is removed at the end.
- **Owner's decision (2026-10-20):**
  - use live staging with **canary values only**;
  - no throwaway Fly app, no real secret value, no redeploy of the running service;
  - nothing touches the running service's machines or `fly.toml`;
  - one session authorizes it all.
- **The kit** is in [`v0.13.0-file-delivery/`](v0.13.0-file-delivery/):
  - `canary/`: the canary generator, the scan, the `/proc` sampler, the MCP capture, the seed check and the in-machine probe;
  - `steps/`: one script per step, plus `lib.sh`, `ci-shell.sh`, `rec.sh` and `teardown.sh`;
  - `kit/`: the canary opv manifest, the consumer, the image and the Kubernetes objects.

## 0. Read first: what preparing this found

These facts change the plan as worded. P0 asks the owner to confirm each one.

1. **There is no Fly app called `journeeze-staging`.** Journeeze staging runs on the shared fleet app **`mcproductlabs-portfolio-staging`**, one always-running machine that hosts every staging product (infra `fly/shared-host/fleet/secrets.toml:29-32`, `fly/shared-host/README.md:3-9`; journeeze `fly.toml:1-10`). `journeeze-staging` is the name of the staging **GitHub App**. The kit targets the fleet app, and three things follow:
   - **The one-off machine receives every staging secret of every product as environment variables.** Fly injects all app secrets into every machine of the app. The kit never prints a machine's environment: the probe reports only the presence of one canary name. Even so, this is the main exposure of the session (see "Riskiest step" below).
   - **A fleet deploy during the session would act on the extra machines.** It would also carry the staged canary names onto the running machine. The infra deploy (`fly/shared-host/deploy.sh:35-83`, `flyctl deploy` at `:71`) lists, scales and starts machines. The session therefore needs a deploy freeze (P0d).
   - **The infra launcher forwards only declared names** (`fly/shared-host/README.md` "launcher"). Even if a canary name reached the running machine, no product container would see it.
2. **There is no staging Kubernetes cluster.** The §12.1 Kubernetes steps (V2, V7–V9, V11, V12, V14, V16, V17) need the local throwaway kind cluster of O7 ("local"), which the owner allowed for 0.11.0. In this runbook, "live staging targets" means two things:
   - the real 1Password account, with canary vaults and a real CI service account;
   - the live fleet app, through a **Fly leg** added to A4: V4f, V5f, V6f and V11f stage canary names with no deploy.
3. **At v0.13.0, the MCP `delivery_preview` refuses a role-scoped product.** `src/mcp.rs:1523-1530` calls `delivery_preview::build_for(…, None, None, …)` with no role. For Journeeze's keys (all role-scoped) it replies `choice_required` ("this command needs --role, one of migrate, serve"), exit 2. This was observed offline with the v0.13.0 release asset against `kit/opv/secrets.toml`, with no `op` on PATH. As a result:
   - A4-V16's MCP channel captures that refusal (zero hits expected; nothing to leak);
   - A2's claim "absent from the `opv_state delivery_preview` reply" holds only trivially for role-scoped products.
   - **Suggested follow-up:** add `role` to `opv_state` `delivery_preview`.
4. **opv is non-dumpable**, so its own user can't read `/proc/<pid>/environ` (`src/hardening.rs`). The sampler records that as `env_hits=unreadable`, never as zero.
5. **F1 and F4 can only be answered by proxy** under the decision:
   - **F1:** `fly.toml` `[[files]]` takes effect only through a `fly deploy`. A5-F1 instead compares the Machines API `files` field, set by `--file-secret`, with the same field set through `--machine-config`. That field is what a `[[files]]` entry becomes.
   - **F4:** `fly secrets deploy` restarts every machine of the app. A5-F4 instead tests a restart and an update of the one-off machine only.
   - A literal answer to either needs a separate owner decision.

**Riskiest step: A5-F2,** the first one-off machine in the shared fleet app.
- **Exposure.** The machine holds every staging secret of every product in its environment while it lives. Fly may also print boot output to the app's logs.
- **Collateral damage.** A wrong flyctl call (a deploy, a scale, an update of the wrong machine) would hit the running service. `lib.sh` `flysafe` refuses all of these, and refuses any machine id the kit didn't create (dry-tested with a fake flyctl).
- **Limits.** The machine has no services and no DNS registration, uses `--restart no`, and ends itself after 90 minutes. Teardown T1 destroys it, and T3 proves the running machines and the release version are unchanged.

## 1. Rules for every step

- **Values.**
  - Only canaries from `canary/gen-canary.py` are used: each one carries the run prefix `opvcanary<8 hex>`, and hosts use the reserved `.invalid` domain.
  - The generator writes only to tmpfs outside a git tree, and prints only the run id.
  - A token is pasted at a hidden prompt (`steps/ci-shell.sh`). It is never an argument or a file in the kit, and never echoed.
- **Fly.**
  - Every flyctl call goes through `flysafe` or `flyq` in `steps/lib.sh`.
  - These are refused: `deploy`, `secrets deploy`, `secrets set`, `scale`, `apps`, `machine start` and `machine clone`; `secrets import` or `unset` without `--stage`; an unset of a name that doesn't start with `OPVCANARY`; a machine command on an id the kit didn't create; a `machine run` not named `opvcanary-*`; `fly logs` without `--machine`; any app that isn't the one confirmed in P0; and any app whose name has a `prod`, `production` or `prd` segment.
  - `opv sync verify-fly` never gets `--deploy`.
- **Recording.**
  - Every step runs as `bash steps/rec.sh <script>`, which appends to `$S/evidence/transcript.txt` under `script`.
  - Each automatic verdict prints a `CHECK <ID> <name>: pass|FAIL (<detail>)` line.
  - `RECORD` lines name what the operator must read and write down.
- **Stopping.** If a step prints `refused`, or a `CHECK` fails where the expected result isn't marked UNSURE, stop and record. Then either continue with the next independent step or go to teardown. Never retry a live write with different flags.

## 5. A5: Fly file delivery, F1–F4 (CI-like shell, which holds the app-scoped token)

All of A5 uses one canary secret, `OPVCANARY_A5_FILE`, which is the base64 of `$CANARY/a5/file-v1.raw` (and later v2). That content holds CRLF, a NUL, `0xFE 0xFF` and trailing spaces, so a decode or newline change shows. The file is requested at three paths, so that "where does it land" has a contrasting answer:
- `/dev/shm/opvcanary/a5-file`: Journeeze's `JZ_VAULT_DIR` parent, usually tmpfs;
- `/run/opvcanary/a5-file`;
- `/opt/opvcanary/a5-file`: certainly on the root filesystem.

`canary/a5-probe.sh` runs inside the machine (sent base64-encoded through `flyctl machine exec`). It prints, per path, presence, mode, owner, size, SHA-256, filesystem type and mountpoint. It also prints the mount table rows for `/`, `/dev/shm`, `/run`, `/opt` and `/tmp`, whether `OPVCANARY_A5_FILE` is present **as an environment variable** (presence only), a sentinel's presence and the boot id. It never prints content or the environment.

### A5-F0: baseline and stage the canary file secret
- **Run:** `a5-f0.sh`: the baseline (if V4f didn't take it), then `flysafe secrets import --stage < $CANARY/a5/import-v1` (stdin, never argv), then `secrets list` for that name.
- **Proves:** the precondition, which is the §7.2 base64 staging through stdin.
- **Expected:** one name, `Staged`.
- **Record:** the status and the release version.
- **Live write:** **1 staged Fly secret.**
- **Rollback:** T2.

### A5-F2: where does the file land? (machine A)
- **Run:** `a5-f2.sh`: `flysafe machine run <debian:trixie-slim@sha256:a292…> sleep 5400 --name opvcanary-a5-a --region iad --restart no --skip-dns-registration --vm-size shared-cpu-1x --metadata opv_live_check=a5`, with `--file-secret <path>=OPVCANARY_A5_FILE` for each of the 3 paths. Then the probe.
- **Answers F2:** filesystem type, mode and owner per path.
- **Expected:** **unknown**; this is the question. How to read each outcome:

| Outcome | Meaning for §7.3 / #274 |
|---|---|
| `/dev/shm` path present, `fs=tmpfs` | Fly can deliver into RAM: `[[files]]` under Journeeze's `JZ_VAULT_DIR` keeps the RAM-only property |
| `/dev/shm` or `/run` path **absent**, `/opt` present | the file is written before a tmpfs is mounted over that path (shadowed): Fly's files go to the root filesystem only, which breaks the RAM-only property; the shim stays and the approach needs rethinking (#274 §1) |
| every path present, all on the root filesystem type (for example `overlay` or `ext4`) | the file is on the machine's disk |
| `env OPVCANARY_A5_FILE: present` | the file secret is **also** an environment variable on every machine of the app, so shim retirement doesn't take values out of the environment by itself |

- **Record:**
  - the probe output (`$E/a5/f2-probe.txt`): per path, presence, `fs`, mountpoint, `mode`, `owner`, `size`;
  - the mount rows;
  - the env line.
- **Live write:** **one machine** in the fleet app. It has no services, so no traffic reaches it, and it stops itself after 90 minutes.

- **UNSURE:**

  - whether flyctl's `machine exec` takes the probe string as one command.

## 6. The canary scan

- **Generator** (`canary/gen-canary.py`):
  - **Values.** 12 values plus the rotation plus 2 A5 file versions. Each holds `opvcanary<run>`; URLs use `db.invalid` and `otel.invalid`; the "PEM" is headed `OPV CANARY NOT A KEY`, so no secret scanner mistakes it for a key.
  - **Refusals.** It refuses an output directory that is not tmpfs or that is inside a git tree.
  - **Output.** It writes `expect/*.txt` with SHA-256 values and the prefix only hex-encoded (safe to mount into the cluster).
  - **Patterns.** `patterns.txt` holds the prefix, the base64 (standard and URL-safe) of every full value, and the base64 forms of the prefix at all three byte offsets.
  - **Self-test.** `--self-test` checks:
    - every value carries the prefix;
    - the webhook canary fits Journeeze's real rule;
    - every needle is found at every offset;
    - no pattern hits ordinary command lines, `OPVCANARY__…` names or random base64.
- **Channels:**

| Channel | Captured by | Step |
|---|---|---|
| stdout/stderr of every command | `script` transcript | all |
| argv and environment of opv, op, flyctl, kubectl, docker | `canary/proc-sampler.sh` (in memory; writes counts, variable **names** and argv[0..2], never a command line or an environment) | V5, V5f, V10, V11, V11f, V15 |
| MCP preview | `canary/mcp-preview.py` (`opv_state` `delivery_preview`) | V4 |
| CLI preview, plans, status, delivery JSON, receipts | `$E` | V4, V4f, V5, V5f, V11 |
| Kubernetes objects, events, pod logs, node `/var/log/pods` | `a4-v16.sh` | V16 |
| Fly `secrets list`, machine configs, the kit machines' `fly logs`, in-machine probes | `a5-f5.sh`, `a4-v16.sh` | F5, V16 |

- **Excluded.** Only the stores' own data: Secrets and ConfigMaps labelled `opv-managed`, and the 1Password items. These hold the values by design.
- **Exit codes:** 0 means pass, 1 means a hit (reported as `file:line`, never the line), and 2 means the scan did not run completely (missing or empty channel, or a failed positive control). A 2 is never a pass.
- **Tested while preparing:** pass, hit and did-not-run cases against a generated set; the sampler caught a canary in a fake process's argv (redacted) and environment (variable named).

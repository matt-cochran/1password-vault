# opv v0.13.0: live checks for #136 (A4, A5), runbook

This is the runbook for the last live checks of #136. The owner runs it top to bottom in one session. **Status: kit only, not run yet.** Nothing in this file or its directory has touched Fly, 1Password or a cluster. The `live-record` lane fills the results tables (§8) from the session's evidence.

- **A4** is the tagged-release verification. It runs `docs/design/delivery-transports.md` §12.1 V1–V17 against the published **v0.13.0** release (tag `v0.13.0` = `ff81d31c141389dc99620f21de54fa2cc1534993`), using canary values only.
- **A5** is the Fly live check. It answers F1–F4 of §7.3 (`journeeze-saas#274` §1) **directly**, on a throwaway app.
- **Owner's decisions:**
  - **2026-10-20:** canary values only, no real secret value, one session authorizes it all.
  - **Revised the same day:** the Fly checks run on a **dedicated throwaway Fly app, `opv-136-canary`, that holds only canaries.** Nothing touches the shared staging fleet app or anything in production.
- **The kit** is in [`v0.13.0-file-delivery/`](v0.13.0-file-delivery/):
  - `canary/`: the canary generator, the scan, the `/proc` sampler, the MCP capture, the seed check and the in-machine probe;
  - `steps/`: one script per step, plus `lib.sh`, `ci-shell.sh` and `rec.sh`;
  - `kit/`: the canary opv manifest, the minimal `fly.toml`, the consumer, the image and the Kubernetes objects.

## 0. Read first

1. **Why a throwaway app.** Journeeze staging runs on a shared fleet app that hosts every staging product. Fly gives every app secret to every machine as an environment variable, and a fleet deploy acts on every machine in the app. A one-off machine there would have held every product's real staging secrets, and F1/F4 could only have been answered by proxy. The owner therefore chose a dedicated app. On that app:
   - every secret is a canary;
   - `fly deploy` and `fly secrets deploy` are safe to run, so **F1 and F4 are answered literally**;
   - the app is destroyed at the end (T2), and its token is shown to be dead (T3).
2. **There is no staging Kubernetes cluster.** The §12.1 Kubernetes steps (V2, V7–V9, V11, V12, V14, V16, V17) run on the local throwaway kind cluster of O7 ("local"), as in 0.11.0. A4's **Fly leg** (V4f, V5f, V6f, V11f) syncs canaries to the throwaway app.
3. **At v0.13.0, the MCP `delivery_preview` refuses a role-scoped product.** `src/mcp.rs:1523-1530` calls `delivery_preview::build_for(…, None, None, …)` with no role. For Journeeze's keys (all role-scoped) it replies `choice_required` ("this command needs --role, one of migrate, serve"), exit 2. This was observed offline with the v0.13.0 release asset against `kit/opv/secrets.toml`, with no `op` on PATH. As a result:
   - A4-V4 expects that refusal, and A4-V16 scans it;
   - A2's claim "absent from the `opv_state delivery_preview` reply" holds only trivially for role-scoped products;
   - **suggested follow-up:** add `role` to `opv_state` `delivery_preview`.
4. **opv is non-dumpable**, so its own user can't read `/proc/<pid>/environ` (`src/hardening.rs`). The sampler records that as `env_hits=unreadable`, never as zero.

**Riskiest step: A5-F1,** the first `fly deploy` and `fly machine run` of the session. They are the only commands that create machines, and a wrong `--app` would act on another app.
- `flysafe` forces `--app` to the throwaway app and refuses any `-a`, `--app`, `-o` or `--org` argument.
- It refuses any app that isn't the confirmed `opv-136-canary*`, any `mcproductlabs-*` fleet app, any app with a `prod`, `production` or `prd` segment, and an app that differs from the manifest's `fly.app`. All of this was dry-tested with a fake flyctl.
- The token is scoped to the throwaway app only.
- The minimal `fly.toml` has no services, and the deploy uses `--no-public-ips`, so nothing is reachable.

## 1. Rules for every step

- **Values.**
  - Only canaries from `canary/gen-canary.py` are used: each one carries the run prefix `opvcanary<8 hex>`, and hosts use the reserved `.invalid` domain.
  - The generator writes only to tmpfs outside a git tree, and prints only the run id.
  - A token is pasted at a hidden prompt (`steps/ci-shell.sh`). It is never an argument or a file in the kit, and never echoed.
- **Fly.**
  - Every flyctl call in a step goes through `flysafe` or `flyq` (`steps/lib.sh`), which act on the throwaway app and nothing else.
  - On that app, deploys, `secrets deploy` and machine commands are allowed.
  - `apps …` and `tokens …` are refused in steps. Creating the app (P5) and destroying it (T2) are the owner's own commands.
- **Recording.**
  - Every step runs as `bash steps/rec.sh <script>`, which appends to `$S/evidence/transcript.txt` under `script`.
  - Each automatic verdict prints a `CHECK <ID> <name>: pass|FAIL (<detail>)` line.
  - `RECORD` lines name what the operator reads and writes down.
- **Stopping.** If a step prints `refused`, or a `CHECK` fails where the expected result isn't marked UNSURE, stop and record. Then continue with the next independent step, or go to teardown. Never retry a live write with different flags.

## 5. A5: Fly file delivery, F1–F4, answered directly (CI-like shell)

All of A5 uses one canary secret, `OPVCANARY_A5_FILE`, which is the base64 of `$CANARY/a5/file-v1.raw` (later v2). That content holds CRLF, a NUL, `0xFE 0xFF` and trailing spaces, so a decode or newline change shows.

**Two machines, one per mechanism, each at the same three paths:**
- **Machine A** is created by `fly deploy` of `kit/fly/fly.toml`, through three `[[files]] guest_path/secret_name` entries.
- **Machine B** is created by `fly machine run` with three `--file-secret` flags.

**The three paths:**
- `/dev/shm/opvcanary/a5-file`: Journeeze's `JZ_VAULT_DIR` parent, usually tmpfs;
- `/run/opvcanary/a5-file`;
- `/opt/opvcanary/a5-file`: certainly on the root filesystem.

**Image.** `debian:trixie-slim` pinned by digest, the same base as `kit/Dockerfile`, with `sleep` as the process. It was chosen over the kit's consumer and over busybox:
- coreutils `stat` and `df -T` and `/proc/self/mountinfo` give the filesystem type, mode, owner, inode and mtime, which is what F2 needs;
- the consumer would also need a registry push and only says `match`;
- busybox's `stat` and `df` vary by build.

**The probe.** `canary/a5-probe.sh` runs inside a machine (sent base64-encoded through `flyctl machine exec`). It prints, per path, presence, mode, owner, size, inode, mtime, SHA-256, filesystem type, mountpoint and directory mode. It also prints the mount rows for `/`, `/dev/shm`, `/run`, `/opt` and `/tmp`, whether `OPVCANARY_A5_FILE` is present as an environment variable (presence only), the sentinel and the boot id. It never prints content or the environment. It was tested locally: it prints metadata and digests only, and the digest matches `file-v1`.

### A5-F2: where does the file land, with what mode and owner?
- **Run:** `a5-f2.sh`, which reads both machines' probes from A5-F1.
- **Answers F2's first half directly.**
- **Expected:** unknown; this is the question. How to read each outcome:

| Outcome | Meaning for §7.3 / #274 |
|---|---|
| `/dev/shm` path present, `fs=tmpfs` | Fly delivers into RAM: `[[files]]` under Journeeze's `JZ_VAULT_DIR` keeps the RAM-only property |
| `/dev/shm` or `/run` path **absent**, `/opt` present | the file is written before a tmpfs is mounted over the path (shadowed): Fly's files land on the root filesystem only, which breaks the RAM-only property; the shim stays and the approach needs rethinking (#274 §1) |
| every path present, all on the root filesystem type (for example `overlay` or `ext4`) | the file is on the machine's disk |
| `env OPVCANARY_A5_FILE: present` | the file secret is **also** an environment variable on every machine of the app, so shim retirement doesn't take values out of the environment by itself |

- **Record:** per machine and path: present or absent, `fs`, mountpoint, `mode`, `owner`, directory mode; and the env line.

## 6. The canary scan

- **Generator** (`canary/gen-canary.py`):
  - **Values.** 12 values plus the rotation plus 2 A5 file versions. Each holds `opvcanary<run>`; URLs use `.invalid`; the "PEM" is headed `OPV CANARY NOT A KEY`.
  - **Refusals.** It refuses an output directory that is not tmpfs or that is inside a git tree.
  - **Output.** `expect/*.txt` holds SHA-256 values and the prefix only hex-encoded.
  - **Patterns.** `patterns.txt` holds the prefix, the base64 (standard and URL-safe) of every full value, and the base64 forms of the prefix at all three byte offsets.
  - **Self-test.** `--self-test` checks:
    - every value carries the prefix;
    - the webhook canary fits Journeeze's real rule;
    - every needle is found at every offset;
    - no pattern hits ordinary command lines, `OPVCANARY__…` names or random base64.
- **Channels:**

| Channel | Captured by | Step |
|---|---|---|
| stdout/stderr of every command | `script` transcript | all |
| argv and environment of opv, op, flyctl, kubectl, docker | `canary/proc-sampler.sh` (in memory; writes counts, variable **names** and argv[0..2], never a command line or an environment) | V5, V5f, V10, V11, V11f, V15 |
| MCP preview | `canary/mcp-preview.py` | V4 |
| CLI preview, plans, status, delivery JSON, receipts | `$E` | V4, V4f, V5, V5f, V11 |
| Kubernetes objects, events, pod logs, node `/var/log/pods` | `a4-v16.sh` | V16 |
| Fly secrets list, machine configs, releases, the app's logs, in-machine probes | `a5-f5.sh`, `a4-v16.sh`, `t1-kind-scan.sh` | F5, V16, T1 |

- **Excluded.** Only the stores' own data: Secrets and ConfigMaps labelled `opv-managed`, and the 1Password items.
- **Exit codes:** 0 means pass, 1 means a hit (reported as `file:line`, never the line), and 2 means the scan did not run completely, which is never a pass.
- **Re-tested for this revision:** scan exits 0, 1 and 2 in the matching cases; the sampler named `LOG_LEVEL` and never wrote the canary; the probe prints metadata and digests only.

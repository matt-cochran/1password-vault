## 1. Strengths to keep

- **One verb per job, read before write.** `check` (local, no target), `status` (both sides), `plan` (dry run), `sync` (write), `run` (local exec). Destructive actions are separate flags (`--deploy`, `--prune`, `--rotate`, `--prune-immutable`), and the help says so plainly: "Nothing is deployed or removed without the flags below."
- **Errors name the fix and list the valid choices.** `undefined environment "nope" (defined: dev, prod, staging)`, `--product is required. Choose one of: api. Usage: opv run dev --product <name> -- <command>`, clap's `tip: some similar subcommands exist: 'setup', 'status'`.
- **Stable exit codes, including 8 (findings) and 9 (unknown, safe to re-run).** CI can tell "fix something" from "re-run" without parsing text.
- **`doctor` uses a fixed line format** (`ok/warn/FAIL/skip  <check>: …`) and ends with exactly one `Next step` line. It is scoped by `--env/--product`, so local work never needs deployment CLIs.
- **`explain` works offline** and prints the `op://` reference plus an `op item get` inspect command that never includes `--reveal`.
- **JSON is versioned** (`schema_version: 1`, and adding fields does not bump it). It contains names and states only, never values.
- **`using <path>` on stderr** makes the config walk-up visible without polluting stdout or JSON.
- **The output is pipe-safe** (`status | head` works) and nothing prompts outside `setup`/`session`. Both of those refuse without a TTY before any vendor call.
- **Progress, retry and interruption lines** (`retrying op item get (2/3) in 1.0 s`, `waiting for revision … 45 s`, `interrupted during <step>; safe to re-run`) go to stderr, so JSON stays clean.

Same concept, different words in the Fly and pinned sync flows: `not desired here, kept (pass --prune to unset)` vs `(pass --prune to remove)`; `staged changes not deployed (no --deploy)` vs `pending deploy (pass --deploy): …`. Status summary says `(staged by the next sync)` on Azure/K8s, where the word is "written" (`src/app/status.rs:184`).

24. Status and check JSON differ in shape: check's keys are alphabetical with top-level `findings` and `target_checked`, and rows have no `kind`. Status has `totals.findings` and rows with `kind`. Both are schema 1.

**Help text**

25. Root help: `Advanced commands remain available below.` is printed *after* the command list. The example columns are misaligned by one (`opv item skeleton staging`, `opv check dev --product api`).
26. `session --help`: `--account` and `[COMMAND]...` have empty descriptions.
27. Global options interleave with command options (for example `sync --help`: `--prune`, `--timeout`, `--rotate`, `--verbose`, `--prune-immutable`).
28. `--config` is described as "Path to the *fleet* configuration", which confuses simple-profile users. `init --help` lists `--config`, which `init` then refuses.
29. The quick start shows `opv check dev --product api` and `opv run dev --product api …`. Under the simple profile both are configuration errors (`--product is not used under the simple profile`).

**Secret-safety observation (design, not CLI wording)**

30. opv-k8s names each Secret `opv-<name>-<10 hex of the value's SHA-256>` (`src/adapters/kubernetes/config.rs:382`; `docs/configuration.md`). Anyone who can *list* Secrets (often a broader right than *get*) sees a 40-bit fingerprint of the value, and a low-entropy value (PIN, short password, enum-like secret) can be confirmed offline. A keyed HMAC is not possible without state. Consider a counter or 1Password field-version based suffix, or document the trade-off in SR terms before 0.5.0.

## 4. The five to do before 0.5.0

1. **P1, the `Next:` contract.** Agents and CI are told it exists (agent-setup rule 5, CHANGELOG). Today four spellings coexist, and one of them (`check`) labels guidance as a command. This is also the cheapest way to make every error act as an instruction.
2. **P2, one run summary plus `sync --json`.** 0.5.0 adds two providers whose sync output uses different vocabulary from Fly's. One summary block (and its JSON) gives every user the same "did it go live?" answer, and delivers a promise already in the CHANGELOG. The golden churn is intended and best done once, now.
3. **P4, provider-neutral wording, plus fixing bugs 18–24.** The release is about Azure and Kubernetes. Help that says `5 Fly`, `op or flyctl`, `fly name` and "Key Vault" in K8s drift lines undercuts "every command is the same for all of them" (README). The changes are mostly text, and the JSON part is additive.
4. **P3 and P7, the first-run router and `opv session` sign-in advice.** Together they remove the onboarding dead end (`Run opv setup` → `[SETUP-RECIPE] …`) and the clash between the "no shell exports" guided flow and doctor's `eval $(op signin)`. Both are text-only, S effort, and fix the first five minutes of use.
5. **P10, `confirm_env`: ship it or strip it.** It is the only *safety* promise in the 0.5.0 docs that no branch delivers, and llms.txt tells assistants to ask before using `--confirm`. Shipping a documented guard that does not exist is worse than not having one. If it cannot land, remove it from CHANGELOG, usage.md, configuration.md, agent-setup.md and llms.txt, and resolve every verify marker in the same pass.

Close runners-up: P6 (`doctor --env` proves the item is readable) and P16 (diagnose before retrying). Both are small and remove the most common "doctor said ok, then check failed" confusion.

# S-238 spike: Azure Container Apps Jobs (live recon)

Status: done; the findings feed `azure-jobs.md` (post-spike revision), and the recorded outputs are
the job adapter's test inputs in `tests/fixtures/azure/jobs/` (R10).

Date: 2026-10-23. The owner approved throwaway resources in the sandbox subscription, resource
group `opv-spike-rg`. The run reused the P1 Key Vault (RBAC model), Container Apps environment
(Consumption, eastus2) and app. Only one manual-trigger job, one user-assigned identity, one role
assignment and three versions of one marker secret were created, and all were deleted at the end.
The environment has no Log Analytics workspace, so no execution log was read. Each execution's
container checked the byte length of its variable against the expected marker's and exited 0 only
on a match. The execution's **status** is the answer, and no value or length left the container.
Tools: `az` 2.91.0. Every job command used is core with `AZURE_EXTENSION_USE_DYNAMIC_INSTALL=no`
(J1). Marker values only (`opv-spike-marker-j*`), always on stdin. The scripts, raw outputs and
logs stay in the session scratchpad, outside the repository.

Two runs: the first stopped at W2 (`unrecognized arguments: -c echo created`), because `az`'s
argument parser takes a value that starts with `-` as a flag. That was the script's mistake, and it
does not matter to opv, which never creates jobs. The rerun created the job
with `--command /bin/true` and set the real command in the stdin document. It used secret name
`OPV-SPIKE-JOB-238B`, because the first run's secret stays soft-deleted (P1 Q4). Cleanup ran after
both runs. The resource group matched its baseline (R2) afterwards, and W11 found no marker
anywhere.

| # | Question | Finding | Consequence |
|---|---|---|---|
| J1 | Are the job commands core, with no extension prompt? (R1, R5) | `containerapp job {create,show,list,update,start,execution list/show,identity assign/show/remove,delete}` are core in 2.91.0. `job update --yaml` exists. There is no `job logs` command, and `monitor log-analytics query` is an extension. | The job adapter uses the pinned `az` environment unchanged (R7). It never needs logs. No `az rest` fallback is needed for updates. |
| J2 | The shape of `job show` (W2, `containerapp-job-show.json`) | `properties` holds `configuration` (`secrets`, `triggerType`, `manualTriggerConfig`, `replicaTimeout`, `replicaRetryLimit`, `identitySettings`, `registries`, `dapr`, …), `template.containers[]` with `env`, `environmentId`, `workloadProfileName`, and the status fields `provisioningState`, `outboundIpAddresses` (hundreds of entries) and `eventStreamEndpoint`. `configuration.secrets` is `null` on a new job. **No `etag`** (Q8 analog). | The job's read-only list for the fingerprint is `provisioningState`, `outboundIpAddresses`, `eventStreamEndpoint` and `systemData`. `secrets: null` must read as empty. Concurrency is checked by fingerprint before and after, as for the app. |
| J3 | A Key Vault reference added **before** the job identity has any grant (W3, `containerapp-job-update-keyvault-ref.json`, `containerapp-job-execution-show-failed.json`) | **Accepted**: exit 0 after 21 s, and the job reads `provisioningState: Succeeded`. The next execution **Failed**, with no reason field and no `endTime`. The same template succeeded once the grant applied (J5), so the failure is the identity's missing access (inferred: nothing else changed). This is unlike an app, whose update Azure refuses synchronously in this case (P1 Q14). | Nothing on the job shows the problem; only the next execution fails, and the failed execution does not say why. opv must **check the job identity's access before it updates the job**, and refuse with the grant command. Doctor's advisory line alone is not enough for jobs. |
| J4 | Does doctor's grant command work verbatim for a job principal? (W4, `role-assignment-list-job-principal.json`) | `az role assignment create --assignee-object-id <job principal> --assignee-principal-type ServicePrincipal --role "Key Vault Secrets User" --scope <vault id>` succeeded. `role assignment list --assignee … --scope … --include-inherited --include-groups` listed it **at once**, with `roleDefinitionName` and `createdOn`. (The `create` reply has `roleDefinitionName: null`; the list has the name.) | `check_access`'s RBAC reads and command text carry over to jobs unchanged. The listing proves the grant exists, not that it is in effect (J5). |
| J5 | How long until a fresh grant is in effect? (W4b, W5) | Grant `createdOn` 17:38:10. An update sending the W3 document again was accepted. An execution started at 17:38:38 (28 s after the grant) still **Failed**. The next one, at 17:40:28 (2 min 18 s after), **Succeeded** and read v1. | A grant listed by `role assignment list` can take a few minutes to apply (observed between 28 s and 2 min 18 s). opv cannot probe that as the job's identity. Right after a fresh grant, sync proceeds and **warns** that an execution started in the next minutes may fail. It neither waits nor refuses. |
| J6 | A job's own plain secret sent back without its value (W5, `containerapp-job-show-plain-secret.json`, `containerapp-job-execution-show-succeeded.json`) | `job show` lists the plain secret as `{"name": "plain1"}` with no value. An update sending that document back (plus an unrelated env change) was accepted, and the next execution **Succeeded** with the plain secret at its original length. Azure kept the value (Q5 analog). | The job adapter sends unmanaged secrets as `show` returns them, as the app adapter does. The pre-spike rule "refuse a job that has its own plain secrets" is dropped. |
| J7 | Does `job show` or `job update` return any secret value? (W2–W7, W11) | No reply held a marker, and neither did `~/.azure` or the output folder (W11: 0 files). | Job replies may be parsed and kept in the runtime snapshot like the app's (SR-4). |
| J8 | Repin by changing only a secret's `keyVaultUrl` (W6a, `containerapp-job-show-repointed.json`) | Accepted. The next execution **Succeeded** reading v2 under the unchanged secret name `opv-w3`. Per-version names are not needed for jobs, but opv keeps them so that app and job share one `secret_name` and one binding reader. |
| J9 | Repin while an execution runs, removing the old secret in the same update (W7, `containerapp-job-execution-show-running.json`, `containerapp-job-update-repinned.json`) | An execution started at 17:43:34, checking for v2. During it, one update (29 s) removed `opv-w6v2` and added `opv-w7v3` (v3). The running execution **Succeeded** reading v2, and a new execution **Succeeded** reading v3. | An execution keeps the values it started with. A superseded `opv-` secret of a job is removed in the same update that repins it; a job needs no `serving_refs` equivalent. |
| J10 | What does an execution's own template show? (W3–W7 executions) | Every `secretRef` in an execution's template names one execution-scoped secret, `cappjob-<job name>`, not the job's secret names. | opv reads bindings from `job show` only, never from executions. |
| J11 | `provisioningState` during and after an update (W8, `containerapp-job-provisioning-timeline.json`) | Polled every 5 s: `InProgress` appeared once during each of 4 of the 8 updates, for under 6 s, while `az` was still running. The adapter reads `provisioningState` from the reply: `Succeeded` is done, `Failed` refuses, and `InProgress` (not observed) is polled as the app preflight polls (`settled_app`). |

A configured id with `resourceGroups` still matches. |

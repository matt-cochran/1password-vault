# Snapshot review: opv 0.10.0 error catalog

The owner reads every message opv 0.10.0 can print on failure and signs off below. Design: `docs/design/error-catalog.md` §13.5. Snapshots are regenerated by the tests, never edited by hand. A message you want changed is fixed in `src/cause/render.rs` (or the diagnosis), and its snapshots are regenerated.

## What is here

- **61 scenario snapshots** (`scenarios/*.snap`): one situation each, with the text run, the `--json` run and, where the command has an MCP tool, the MCP answer. Together they reach every error cause except six that are listed as unreachable in `tests/e2e/coverage.rs` (`UNREACHABLE`), each with its reason.
- **432 matrix snapshots** (`<command>__<call>__<fault>.snap`): one recorded fault injected into one call opv makes. Many cells print the same message for a different vault or item. The table below groups them by error code and fault, so you can read one representative per group (51 groups) rather than all 472.
- `SKIPPED.md`: the cells not run, each with its reason (mostly: no recording of rate-limited, server-error or forbidden replies from op, flyctl and gh).
- `COVERAGE.md`: which fault reached which call.

A group with code `no error document` is a fault the command did not report as an error: check that ignoring it is right.

## How to read one

Each snapshot has the text run (stderr: `opv:` line, `checked:`, the tool's scrubbed reply in a box, `Do:`, `Next:`) and the `--json` run (the same content as one `error` object, `schema_version` 2). Check that:

1. the `opv:` line says what failed, in words a person understands, and names the right thing (environment, vault, item, account);
2. `Do:` is what you would actually do;
3. `Next:` is a command you could paste and that makes progress (never the failing command again, unless a sign-in or fix comes first);
4. nothing in the box or JSON is a secret value (1Password values are `********`; IDs and emails in recordings are markers such as `AE2EDEVACCOUNT000000000001`);
5. the JSON says the same as the text.

## Findings

The review was delegated by the owner to Junior (DeepSeek through `junior handoff`), and the manager verified every finding against its snapshot. It ran in three passes:

1. **The full set:** all 61 scenarios and one cell of every matrix group, 125 snapshots, gave 39 findings (17 high). Thirty-four were confirmed and five rejected as not defects. Fixed on `feat/error-catalog`: a probe's runner facts (tool missing, timeout) now come before any inference, the real attempt counts, Next steps that keep `--apply`/`--confirm` and never point at `--help`, the namespace and context in Kubernetes errors, wording, and a simulator fault-mapping bug.
2. **The 32 snapshots changed or added by those fixes:** 11 findings. Eight were fixed (the vault name taken from `op vault list`, an unexplained placeholder, two Next steps, the GitHub environment 404, two Do lines, a harness cell), one was reworded (R2-4) and two were not defects.
3. **The snapshots changed by round 2 and by the move to the owner's recorded op replies:** no new defects.

The triage, with every finding and its outcome, is in `.delivery/v0100/review/TRIAGE.md` (not committed: the review record).

Left for later, needing owner recordings: `op vault user list` without Manage, and `op whoami` with only another account signed in.
